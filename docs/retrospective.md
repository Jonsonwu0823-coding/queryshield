# 问题复盘

开发中遇到的十一个有代表性的问题。每条写现象、怎么发现的、根因、修复、怎么验证、教训，并给出代码或测试位置（相对于本目录）。日期是问题定位和修复的时间。

## 怎么读

- 涉及盲测的条目（第 4、5 条）只写方法，不写盲测题的任何内容。
- “开发集”指开发中反复看过的题，结果只说明在这些题上稳定。
- 第 8 条起的数字（金额、行数）都来自公开的演示数据。

## 1. 检查“全部通过”，其实没检查关键的东西（2026-09，反复出现）

- **现象。** 多次出现检查报告全绿、却没有验证关键性质的情况：数据库检查用有写权限的管理员账号也能通过；统一入口漏注册了三项必需检查，“全部通过”的分母本身是错的；并行查询的检查只断言状态和并发数，把结果注入成 999 照样通过；来源链检查用一份空报告当对照就判通过。
- **怎么发现的。** 复核时故意注入错误（换账号、改数值、删记录、跨租户），看检查会不会变红。
- **根因。** 检查只断言“跑完了”“形状对”，没有断言契约本身；“没运行”和“通过”没有分开记。
- **修复。** 每项检查至少配一个负对照，注入错误后必须失败；统一入口里没注册的必需检查记“阻塞”而不是“通过”；本机和 CI 用同一个入口，它自己核对“实际运行的检查 + 写明原因的排除清单 = 登记的全部检查”。
- **怎么验证。** 改动都配变异测试：把被测代码改坏（或换回修复前的版本），对应的测试必须失败。
- **教训。** 测不出注入错误的检查等于没有；覆盖率只说明代码执行过，不说明结果被断言过。
- **代码与测试。** `scripts/check-all.ps1`；`tests/test_check_all.py`（排除清单与登记表双向核对）；`tests/test_eval_en03_controls.py`（来源链检查的负对照）。

## 2. 崩溃重启后，并行分支永远停在 RUNNING（2026-09-23）

- **现象。** Agent 的并行只读分支在服务崩溃重启后，没有任何代码去扫描和恢复，“不确定是否执行过”的分支会一直停在 RUNNING。
- **怎么发现的。** 原来的检查在同一个进程里手工把状态设成 RUNNING 再调一次调度器，没有真的重启；改成按真实场景跨进程重启后复现。
- **根因。** 恢复逻辑只在调度器下次被调用时触发，服务生命周期里没有启动扫描。
- **修复。** 应用启动时扫描状态库：全部分支都已提交、只差汇总的组，复用已有结果完成，不重跑 SQL；状态不确定的组持久标记为 `FAILED/recovery_required`，SQL 执行次数为 0；取消会等执行器真正退出。恢复承诺明确限定为单进程，不承诺恰好一次。
- **怎么验证。** 历史检查 STATE-RT02 真实地跨进程重启，断言错误码和 SQL、模型调用计数不变。
- **教训。** 不确定就停下交给人处理，比“为保险再跑一次”安全：重复执行在只读查询上是浪费，在有副作用的操作上就是错误。
- **代码与测试。** `src/queryshield/agent/parallel_durable.py` 的 `recover_on_startup`、`_fail_uncertain_group`；`src/queryshield/api/main.py` 的 `_application_lifespan`；`scripts/check_state.py` 的 `check_rt02`。注：产品当前的 HTTP 路径不启用并行分支，启动扫描仍然运行。

## 3. 回答说“引用了资料”，却追不到本次检索（2026-09-26）

- **现象。** 检索指标和 SQL 结果单独看都正确，但 B1 的最终回答声称引用了资料，同一次运行里却没有任何检索记录；检索评测用的是另一套运行标识，连不上产品的回答。
- **怎么发现的。** 端到端核对“回答 → 来源 → 本次检索”这条链时发现链是断的；原来的来源链检查用空报告当对照，判了通过。
- **根因。** 回答里的来源 id 由模型写、没有与本次运行的检索记录比对；离线检索指标衡量的是检索器，不是这一次的回答。
- **修复。** 检索结果沿同一次运行传给模型并记录；回答声明的来源必须属于本次检索实际返回的集合；后来进一步改为：知识类回答的来源 id 由服务端从本次检索里取，不用模型写的。来源链检查加五类负对照：缺少检索返回、跨运行引用、引用未返回的候选、无权限的资料、版本错误。
- **怎么验证。** 五类负对照在测试里都必须被拒绝；有效的来源链形状都必须通过。
- **教训。** 引用可信的前提是能追溯到同一次运行、经过权限过滤的检索结果；离线指标好，不等于产品这一次用了检索到的内容。
- **代码与测试。** `src/queryshield/agent/graph.py` 的 `_verified_answer`；`src/queryshield/evaluation/provenance.py`；`tests/test_eval_en03_controls.py`、`tests/test_provenance.py`。

## 4. 评测把正确答案判成“越权”，而且不能看题来查（2026-09-28）

- **现象。** 盲测中，B1 的一道题被评测观察器判为“未授权事实”（安全硬约束）。
- **怎么发现的。** 盲测结果本身。难点在于定位：盲测题和原始记录是加密的，为了不“对着考题改代码”，定位过程不能看题。
- **根因。** 观察器只认经过记录执行器的结果编号；服务端多段计划合成的结果有一个新的编号，不经过记录执行器，于是被当成来历不明。产品本身是对的。
- **修复。** 只改观察器，不改产品，也不放宽判分。服务端合成的结果只有在以下条件全部满足时才认可：能取到服务端的证据；证据的运行、租户、用户一致；本次运行里恰好有对应的组件查询；用组件查询的哈希重算出的组合哈希与证据一致。任何一步不满足仍判越权。
- **怎么验证。** 先读代码提出假设，在公开的开发用例上用合成数据复现同一类误报；再用一个只在本机运行的脱敏诊断确认：密钥只在内存里，明文不落盘，输出走白名单（只有是 / 否、计数和公开的类型名，不含题目、金额、id）。修复配了伪造证据的测试。
- **教训。** 安全判定要默认拒绝：放宽规则会掩盖真正的越权，所以修的是“能证明来历”的路径，而不是计数。诊断工具的输出用白名单而不是黑名单，新字段不会被意外带出去。
- **代码与测试。** `src/queryshield/evaluation/provenance.py`；`tests/test_provenance.py`。

## 5. 修好了怎么证明：已见数据确认不等于盲测（2026-09-28）

- **现象。** 第 4 条修好之后，需要证明误报消失；但那套盲测题已经打开过、做过诊断，再在上面跑出的分数不再是“没见过的数据”上的成绩。
- **怎么发现的。** 准备复跑时，对照“盲测”的定义发现了这个问题。
- **根因。** 同一批题既用来发现问题、又用来证明修好，会把“针对这批题的改进”算成泛化。
- **修复。** 复跑明确标成“已见数据确认”，所有输出都写明不是盲测并指回原来那次盲测；对外的盲测成绩仍用修复前的 6/8；下一次盲测需要一套新的封存题。证据链逐环记录上一环的哈希（源码清单 → 评测汇总 → 分数 → 加密原始记录 → 诊断），分数由第二个进程独立复算。
- **怎么验证。** 能重跑的步骤（源码清单、校验函数、回归测试、诊断自测）重跑；需要本机密钥或付费模型的步骤，核对哈希链和结论字段，并写明复用了什么、为什么。复核中还发现一条诊断依据不成立（只比较了值、没比较列，相等的值可能来自另一列），于是改为按列名比对。
- **教训。** 分数要和它的数据身份一起报告；值相等不等于来自同一来源。
- **代码与测试。** `docs/evidence.md` 的“盲测”一节记录了当时的成绩和局限。

## 6. 追问与口径：模型判断，服务端从两个方向核对（2026-09-30）

- **现象。** “销售额”在支付订单总额和退款后净额之间含糊，应该先问；“支付金额”是明确的，不该再问。只靠给模型的提示时，真实模型两头出错：开发集上的“销售额”反向题 3 次都没问，明确的“已支付订单总额”却常常追问。
- **怎么发现的。** 开发集 Real 连跑三次的逐题记录。
- **根因。** “要不要追问”只写在给模型的上下文里，服务端既不核对模型问没问，也不核对该不该问；原来的追问触发词里有“总额”“金额”这类泛词，明确的问法也被当成含糊。
- **修复。** catalog 加说法表：每个指标的明确说法、每条追问规则的含糊说法，最长匹配；泛词故意不列。服务端只核对、不替模型选：只有含糊说法却直接选了口径，拦下改为追问（问 catalog 里的固定问题）；已有明确说法却追问，退回一次。退回单独计数，不占 SQL 的修复机会。每个回答末尾写明口径和依据，依据句只能由 catalog 里的名称和说法组成。
- **怎么验证。** 逐个撤掉新加的核对，每处都有测试失败；冻结题逐题判定与改动前 0 差异。开发集 Real 连跑三次：安全违规 0，关键题每次 8/8，“销售额”反向题 3/3。之后收窄了退回的触发条件：只有强信号（规则 id、点名两个取值、规则特有的识别词）才算口径追问，问时间的追问不再被误拦。
- **教训。** 护栏有误判和漏判的此消彼长：识别面放宽，误判变多；收窄，漏判变多。服务端核对模型的决定，和服务端按关键词替模型做决定，是两回事。
- **代码与测试。** `src/queryshield/catalog/phrases.py` 的 `PhraseIndex`；`src/queryshield/agent/tool_execution.py` 的 `check_clarification`；`tests/test_clarification.py`、`tests/test_ask_review.py`。

## 7. 回答契约：模型声明依据，服务端核对；提示管不住时由服务端补一步（2026-10-01）

- **现象。** 判断回答有没有依据的方式太粗：没查询就回答，直接 502，不给修正机会；只看过表结构或检索结果的回答会被放行，客户端也分不出哪句话经过服务端核实；“你好，你能做什么？”这类问题只能得到 502。
- **怎么发现的。** 开发集 Real 里没查询就回答的失败，加上对回答类型的逐一梳理。
- **根因。** 没有让模型说明“这个回答凭什么”，服务端只能事后猜。
- **修复。** `final_answer` 加可选字段 `basis`：`query`（默认，要求本 run 有成功的查询）、`knowledge`（只认本 run 的检索来源，来源 id 由服务端给出）、`no_data`（服务端写固定回复，丢弃模型文字）。没有依据时退回一次，再犯就终止，不返回模型写的文字。响应加 `answer_status`（verified / unverified / no_data）。真实模型遇到定义题时认为自己知道答案、不肯先检索，改提示也没用；最后改为：模型声明 `knowledge` 而本 run 没有检索时，服务端用原问题检索一次（同一个检索器、同样的权限，计入工具调用），再退回。
- **怎么验证。** 契约测试覆盖每种依据和冲突；冒烟按动作轨迹记录“没有依据 → 服务端检索 → 退回 → 答对”，记为已知缺口 `knowledge_after_send_back`。开发集 Real 连跑三次：安全违规 0，8 道关键题都是 3/3。
- **教训。** 提示管不住模型时，不要继续堆提示，而是看服务端能不能替它补上确定的一步；补的那一步不能变成替模型做决定（这里只检索，不选指标、不写回答）。
- **代码与测试。** `src/queryshield/agent/proposals.py`（`basis`）；`src/queryshield/agent/graph.py` 的 `_verified_answer`；`tests/test_answer_contract.py`。

## 8. 数是真的、含义是错的：只有“行范围等于口径范围”才能叫已核实（2026-10-01 至 10-02）

- **现象。** 演示题“7 月已支付金额最高的客户”：服务端把第一名客户的金额 2,872.80 元标成了“7 月支付订单总额，已核实”，真实的 7 月总额是 22,225.00 元。
- **怎么发现的。** 演示数据由固定种子生成，每道题的答案独立算出。这道题的判定原本只比对客户名；读运行摘要时注意到它还带着 1 条已核实事实，而结果只有 1 行、1 次 SQL，1 行里既有名字又有金额，只能来自“按客户分组、取第一名”的查询。随后在修改前的代码上复现了完全相同的输出。
- **根因。** 服务端核对绑定时只看 WHERE 里的过滤条件，不看分组之后的 `ORDER BY … LIMIT 1`；结果恰好 1 行，就被当成全租户总额。同一类变体还有：在连接客户表的 ON 里加一个客户条件、不连表按时间分组取第一名。生成事实的五个地方各自判断，所以要一起修。
- **修复。** 按根因定一条规则，写在一个函数里，五处共用：结果能成为全租户事实，必须没有分组、WHERE 里只有服务端绑定的条件、不连表或只连客户表且 ON 恰好是两个主键等式；其余一律是行集。演示判定加一条对所有题都生效的规则：每条已核实事实都按它的租户、指标、时间窗独立复算比对。同一轮还发现产品的审批从没绑定过权限版本（产品从不把知识快照写进状态库），一并修好：发布幂等、重启不撤回运行期的撤销和改角色、找不到权限来源就不建审批。
- **怎么验证。** 分组、连接、过滤的各种写法都有测试；真实库上的完整路径也测了；变异测试全部被抓到。之后的 Real 演示：7 条已核实事实全部与独立复算一致，这道题标“未核实”、没有事实。
- **教训。** 判定只比对“看得见的答案”会漏掉附带的错误事实；“已核实”的定义要按根因写成一条规则，而不是逐个修写法。
- **代码与测试。** `src/queryshield/facts/facts.py` 的 `is_scalar_metric_result`；`src/queryshield/agent/tool_execution.py` 的 `_metric_scope_filters_match`、`_has_trusted_customer_join`；`src/queryshield/approval/service.py` 的 `_approval_permission`；`tests/test_scalar_facts.py`、`tests/test_approval_permission.py`、`tests/test_demo_judge.py`。

## 9. MCP：协议只是传输，服务端返回的错误码也不可信（2026-10-02）

- **现象。** 两个只读元数据工具改走真实的 MCP stdio 会话后，宿主逐条核对返回的结果，却照单全收服务端返回的错误码：恶意服务端回一个参数类或身份类错误码，run 就被记成安全拒绝（403 DENIED）。另外，Linux 上 uvicorn 收到 SIGTERM 正常退出时不执行 `atexit`，含各租户分块文字的索引临时目录会留下来。
- **怎么发现的。** 用未改动的产品服务端、只在它下面注入故障，走完整的 HTTP 路径：基线上有 4 种错误码能把 run 变成 403 DENIED。目录问题在真实 uvicorn 加 SIGTERM 的测试里复现。
- **根因。** 错误码决定 run 的终态，而 DENIED 是安全语义；让服务端决定终态，等于让不可信的一方给自己的行为定性。宿主发送前已经用同一组函数核过参数和身份，诚实的服务端不会再返回这些码。目录只靠 `atexit` 清理，而 uvicorn 处理 SIGTERM 时先跑完应用的关闭阶段，再重新发出信号结束进程。
- **修复。** 错误码白名单：宿主只原样接受 `retrieval_unavailable`（取决于服务端自己检索器的状态，宿主事先不知道）；上游故障记 `mcp_unavailable` 并标 `failure_source: "upstream"`；其余任何码一律记 `mcp_result_invalid`，run 是 FAILED。索引目录改在 FastAPI 关闭阶段清理，`atexit` 留作兜底。MCP 的其它边界不变：宿主按 run 的身份启动服务进程，结果逐条与宿主自己的目录和索引比对，交给 Agent 的是宿主重建的数据，失败不退回本地工具。
- **怎么验证。** 注入的故障在修复后全部是 FAILED，注入的标记文字没有进入 run、事件、响应或模型请求；真实 SIGTERM 下不再留下目录。
- **教训。** “不可信输入”不只是返回的数据，还包括错误码、状态和任何会影响终态的字段。剩下的边界要写明：恶意服务端仍可以把失败标成上游故障，后果只是失败原因不准。
- **代码与测试。** `src/queryshield/mcp_metadata/verify.py` 的 `checked_error`；`src/queryshield/mcp_metadata/schemas.py` 的 `KNOWN_TOOL_ERROR_CODES`；`src/queryshield/mcp_metadata/launch.py` 的 `cleanup_index_dir`；`tests/test_mcp_host_checks.py`、`tests/test_cleanup_and_error_mapping.py`、`tests/test_mcp_index_cleanup.py`。

## 10. 一条命令跑起来：成功被判成失败，判定漏比对（2026-10-03）

- **现象。** 做成 `docker compose up` 一条命令运行、本机和 CI 同一个检查入口之后，Windows 上的真实模型演示脚本把成功的 `docker compose up --build` 报成失败；对照两次演示的摘要，Fake 比对了 4 条已核实事实，真实模型只比对了 3 条。
- **怎么发现的。** 第一个在 Windows PowerShell 5.1 上复现；第二个是对照两份摘要的计数时发现的。
- **根因。** PowerShell 函数里没被接走的命令输出会和 `return` 的值一起返回：`--build` 的构建日志写到标准输出，函数返回的是“日志行 + 退出码”组成的数组，`-ne 0` 对数组做过滤，结果非空就为真。演示脚本的“没给时间”场景只在“追问时间 → 恢复”这条路径上比对数值，真实模型常常自己定月份、第一次就成功，那条事实就没比对。
- **修复。** 输出交给 `Out-Host`，函数只返回整数，并加一条静态规则：函数里调用外部命令必须接走输出。演示脚本每条路径都比对最终回答里的事实，并加一个不变量：每个场景收尾时，事实条数必须等于比对条数，否则记硬失败 `verified_fact_unchecked`；收尾函数只接受关键字参数，新场景漏传会直接报错。
- **怎么验证。** 用假的 `docker` 跑脚本的行为测试覆盖成功、`up` 失败、演示失败三种情形；把演示脚本换回修复前的版本，新测试大多失败。修复后的真实模型演示比对了 4 条，0 条不一致。
- **教训。** “每个场景记得做比对”靠自觉，不变量把它变成结构上的保证；检查要能被证伪，例如“停止再启动后没有临时目录”在 tmpfs 上恒为真，所以 CI 专门把 `/tmp` 换成命名卷再检验。
- **代码与测试。** `scripts/compose-real-demo.ps1`（`Invoke-Docker`）；`scripts/demo_walkthrough.py` 的 `unchecked_fact_failures`；`deploy/ci-tmp-volume.compose.yaml`；`tests/test_container_files.py`、`tests/test_demo_walkthrough.py`。

## 11. 对外文档里的安全说法，要逐个入口核对（2026-10-03）

- **现象。** “请求人查客户姓名要等同租户审批人批准”这条说法，在主入口 `POST /queries` 上成立；但早期保留下来的单次提案入口 `POST /query-proposals` 没有做敏感字段检查：请求人经这个入口提交一条查姓名的 SQL，直接拿到了行。租户、SQL 子集、只读事务和行级安全在这个入口上仍然生效，所以不会跨租户。
- **怎么发现的。** 写对外文档时逐条核对安全说法，对照 `src/queryshield/api/main.py` 里的全部 HTTP 入口，发现接口说明漏了单次提案入口；再在一次性库上用演示数据和 Fake 模型复现。
- **根因。** 敏感字段检查只放在 Agent 的受控工具里；单次提案入口直接调用受限执行器，而执行器本身不做这项检查。
- **修复。** 先修代码，再发布文档。单次提案入口对能解析的 SQL 调用同一个 `check_sensitive_access`：请求人查姓名返回 403 `approval_required`，审批人照常执行；不能解析的 SQL 原样交给执行器，保持原来的错误码。
- **怎么验证。** `customers.*`、连接、别名、姓名出现在各个位置等写法都有测试，审批人和不查姓名的请求保持原样；冻结评测里经过这个入口的一道写操作题，修改前后的 Fake 逐题记录相同。
- **教训。** 安全性质要按入口逐一验证，不能只验证主路径；规则只放一处，所有入口调用同一个函数。
- **代码与测试。** `src/queryshield/api/main.py` 的 `execute_query_proposal`；`src/queryshield/tools/semantic.py` 的 `check_sensitive_access`；`tests/test_proposal_sensitive.py`。
